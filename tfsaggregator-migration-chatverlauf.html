Analyse: Warum das TFS Aggregator Plugin nicht mehr funktioniert

Zusammenfassung der Ursachen

Der zuletzt unterstützte Stand der Codebase ist Azure DevOps Server 2022.2 RC (Build 19.235.34823.2). Seit der Veröffentlichung von ADOS 2022.2 RTW (19.235.35102.1, Juli 2024) und insbesondere ab dem Sicherheitspatch ADOS 2020.1.2 Patch 15 (März 2025) bricht das Plugin in zwei Klassen zusammen:

1. Fehlende Assemblies zur Laufzeit (Hauptursache, ADOS 2022.2)

Microsoft hat in ADOS 2022.2 die SOAP-basierte Client OM aus dem Standardpfad entfernt:

Fehlende DLLs in Web Services\bin:

  • Microsoft.TeamFoundation.WorkItemTracking.Client.dll → ersetzt durch …ClientSlim.dll
  • Microsoft.TeamFoundation.WorkItemTracking.Client.DataStoreLoader.dll
  • Microsoft.WITDataStore64.dll

Resultierender Fehler (siehe Issue #400):

Could not load file or assembly 'Microsoft.TeamFoundation.WorkItemTracking.Client,
Version=19.0.0.0, Culture=neutral, PublicKeyToken=b03f5f7f11d50a3a'

Crash-Punkt: WorkItemRepository.cs:45 – this.tfs.GetService<WorkItemStore>().

2. NullReferenceException in der Client OM (ab ADOS 2020.1.2 Patch 15)

Selbst mit vorhandenen DLLs schlägt der erste WorkItem-Zugriff fehl (Issue #404):

NRE in Microsoft.TeamFoundation.WorkItemTracking.Client.WorkItemStore.TryGetNodeFromSnapshot
→ ...WorkItemStore.GetNode(Int32 id)
→ Aggregator.Core.Facade.WorkItemRepository.GetWorkItem (line 53)

Crash-Punkt: WorkItemRepository.cs:53.

3. Microsoft hat die WIT/Test Client OM offiziell deprecated

Quelle: WIT Client OM Deprecation. Es werden keine NuGet-Pakete Microsoft.TeamFoundationServer.ExtendedClient für 2022.2 (19.235.x) mehr veröffentlicht – nur 19.225.2 ist verfügbar.

4. Installer-Konditionen blockieren neue Builds

Setup.Aggregator/Product.wxs (Zeilen 347–361) kennt nur Build-Nummern bis 19.235.34823.2 (2022.2 RC). RTW (19.235.35102.1), 2022.2 Patches 1–8 sowie ADOS 2022 Update 1 Patches fehlen.

  • Alternativ: Suchpfad auf Application Tier\Tools erweitern, da Microsoft die fehlenden Client-OM-DLLs nur noch dort ablegt
  • <probing privatePath="…\Tools"/> in app.config des Plugins ergänzen

Strategische Empfehlung

Das Projekt ist seit 2 Jahren offiziell deprecated. Die WIT Client OM ist von Microsoft EOL, und neue ADOS-Builds entfernen aktiv die DLLs. Eine kosmetische Anpassung (A, B, E, G) bringt das Plugin kurzfristig auf 2022.2 RTW zum Laufen, schützt aber nicht vor Patch-15-artigen Brüchen oder ADOS 2025+.

Langfristig: Migration der Wrapper-Schicht (D) auf das REST-basierte WorkItemTrackingHttpClient aus Microsoft.TeamFoundationServer.Client, oder Wechsel auf den von den Maintainern empfohlenen Nachfolger aggregator-cli.

Schritt 7: AssemblyResolver statt Web.config-Probing

Statt die sensible Server-web.config zu ändern, implementiere ich einen AppDomain.AssemblyResolve-Hook im Plugin selbst.

Neue Datei Aggregator.ServerPlugin/AssemblyResolver.cs:

internal static class AssemblyResolver
{
    public static void EnsureRegistered()
    {
        // registriert AppDomain.CurrentDomain.AssemblyResolve einmalig
    }

    private static Assembly OnAssemblyResolve(object sender, ResolveEventArgs args)
    {
        // filtert auf Microsoft.TeamFoundation.*, Microsoft.VisualStudio.Services.*, Microsoft.WITDataStore*
        // probt in:
        //   <InstallPath>\Tools
        //   <InstallPath>\Application Tier\Tools
        //   <PluginDir>\..
    }
}

Aktivierung im statischen Konstruktor von WorkItemChangedEventHandler:

static WorkItemChangedEventHandler()
{
#if ADOS2022u2
    // ADOS 2022.2 RTW removed the legacy Work Item Tracking client OM from
    // Web Services\bin; the assemblies now live in Application Tier\Tools.
    AssemblyResolver.EnsureRegistered();
#endif
}

Der statische Konstruktor läuft vor der ersten Instanzmethode — genau rechtzeitig, bevor TFS-Types geladen werden — ohne den Originalkommentar ("DON'T ADD ANYTHING TO THE INSTANCE CONSTRUCTOR") zu verletzen.

Schritt 11: Verifikation

Das SDK-style csproj nimmt .cs-Dateien automatisch auf — AssemblyResolver.cs wird also ohne expliziten Eintrag kompiliert. Directory.Build.targets importiert References\$(TfsVersion)\config.targets, löst sich korrekt auf References\2022.2\config.targets auf.

Verifiziert mit Grep, dass ADOS2022u2 nur in References/2022.2/config.targets definiert ist und nicht aus Versehen in andere Konfigurationen leakt.

Geänderte Dateien

  • Directory.Build.props: DevelopmentTfsVersion → 2022.2, neue KnownTfsVersion

  • Aggregator.ServerPlugin/WorkItemChangedEventHandler.cs: statischer Konstruktor mit #if ADOS2022u2
  • Setup.Aggregator/Product.wxs: Client+Server-Features 2022.2, getrennte SetProperty
  • build-installer.proj: neuer TfsVersion-Eintrag mit 19.225.2

Was auf dem Windows-Build-System zu tun ist

  1. NuGet-Lockfile generieren (einmalig pro Projekt): 
    msbuild /t:Restore /p:Configuration=Debug-2022.2 /p:RestorePackagesWithLockFile=true /p:RestoreLockedMode=false tfs-aggregator-plugin.sln
  2. Build & Test: 
    msbuild /t:Build /p:Configuration=Release tfs-aggregator-plugin.sln
  3. Plugin-DLLs deployen in C:\Program Files\Azure DevOps Server 2022\Application Tier\Web Services\bin\Plugins\. Bei laufendem Server: w3wp.exe-Recycling abwarten.

Bekannte Risiken

  • Die Microsoft.TeamFoundation.WorkItemTracking.Client-API (NuGet 19.225.2) ist die letzte stabile Version; ein neueres ADOS-Patch könnte erneut binär-inkompatibel werden.
  • Falls 19.225.2 Compile-Fehler wirft (falls Microsoft Methodensignaturen geändert hat), braucht man 19.227.0-preview als Fallback.
  • Der AssemblyResolver ist nur in ADOS2022u2 aktiv — andere Konfigurationen sind nicht betroffen.
  • Die WIT Client OM bleibt deprecated; langfristig führt nichts an einer REST-Migration oder dem Wechsel zu aggregator-cli vorbei.
